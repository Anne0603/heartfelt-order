## 二、系統是做什麼的

給手作/烘焙類小型工作室用的**訂單管理系統**：接單、追蹤出貨與收款、
管理自製商品的配方與成本、管理現貨庫存與包材、客戶資料、營運報表。
整體設計以手機操作為主（大部分畫面針對手機瀏覽器最佳化），也支援
桌面瀏覽器與「加到主畫面」的 PWA 獨立模式。

---

## 三、技術架構細節

- **前端**：不使用任何框架（沒有 React/Vue），純 Vanilla JavaScript
  ES Modules，每個功能模組獨立成一個 `.js` 檔案，用 `import`/`export`
  互相引用。
- **登入**：Google 帳號登入。一般瀏覽器分頁用 Firebase Auth 的整頁
  轉跳（`signInWithRedirect`）；「加到主畫面」的獨立模式因為平台
  限制改用 Google Identity Services（GIS）官方登入元件，兩條路徑
  各自獨立運作。
- **資料庫**：Firestore（NoSQL 文件資料庫），權限規則寫在
  `firestore.rules`，修改後需要手動貼到 Firebase Console 發布。
- **圖片儲存**：Cloudinary（商品照片、收據照片等），前端直傳、
  不經過自己的伺服器。
- **快取版本號機制**：所有 `js/*.js` 檔案之間的 `import` 語句、以及
  `index.html` 引用 `css/style.css` 都帶有 `?v=日期-序號` 的版本號
  字串，每次部署遞增，確保瀏覽器會重新下載最新版本、不會卡在舊快取。
  **CSS 檔案也要跟著一起遞增版本號**，不能只處理 JS（這是曾經踩過的坑）。
- **PWA**：`manifest.json` + 圖示（`icons/`），支援加到手機主畫面、
  獨立模式開啟（沒有網址列）。

並指定角色才能真正使用系統。

## 五、主要功能模組

### 訂單管理
新增/編輯訂單、登記出貨（會自動扣庫存）、登記收款、作廢（可還原
庫存）、退貨（部分或全部，可選擇是否加回庫存）、批次列印出貨單
（A4 橫向）、批次標記出貨。

特色設計：
- **「待確認」標記**：訂單資訊還沒跟客戶核對清楚時可以標記，列表/
  詳細頁有明顯提示，出貨後自動不再顯示（沒意義了）。
- **「已作廢」需超級管理員複核**：管理員作廢的訂單會標記待複核，
  超級管理員可以一鍵「確認無誤」；超級管理員自己作廢的直接視為
  已確認。所有作廢訂單都有明確狀態（待確認/已確認），不會曖昧不清。
- **出貨前有二次確認**，避免手滑誤觸（比作廢輕量，不用輸入文字）。
- 訂單列表預設只讀近 3 個月資料（效能考量），套用特定篩選（逾期、
  待確認、已作廢等）會自動展開讀取全部歷史。
- 同一天的訂單依建立時間排序（Firestore 只精確到日期，額外在前端
  用 `createdAt` 補做第二層排序）。

### 商品與庫存
三種商品類型：
- **自製商品**：自己現做的東西，不追蹤庫存量，成本＝配方加總。
- **現貨商品**：進貨轉賣，有庫存追蹤，成本＝加權平均進貨價。
- **包材**：只能被拿去當配方的一部分，不能直接被訂購。

**巢狀配方**：自製商品的配方除了包材，也能加入其他自製商品（例如
禮盒裡裝了幾顆單顆蛋黃酥），系統會自動遞迴展開算出真正的成本、
出貨扣庫存、備料需求。配方列可以個別勾選「不計入這個子項目自己的
包材」，避免散裝進禮盒時包材被重複計算。

商品/客戶都有進貨、盤點、領用等記錄功能。

### 備料清單
彙總所有「還沒出貨」的訂單，算出每個商品要準備幾份，自製商品自動
展開配方（含巢狀），包材/原料需求跟現有庫存比對算出缺口。可以用
預計出貨日期區間篩選。

### 客戶與廠商
客戶/廠商資料、訂購管道統一用下拉選單、客戶詳細頁看得到訂購紀錄
（用客戶固定 ID 比對，不受改名影響）。

### 統計報表 / 利潤總覽
營收/成本/毛利統計、應收帳款總額、商品銷售排行（用商品固定 ID
分組，不受改名影響）、庫存價值、退貨自動沖銷相關數字。

### 支出管理
記錄營業支出，用在利潤總覽的成本計算。

### 常見問題
依角色自動篩選內容的說明頁面，側邊欄所有人都看得到。

### 超級管理員專區
- Cloudinary 設定
- 分類/單位管理
- 一鍵資料備份（匯出 JSON）
- **重算訂單成本**：商品配方調整後，一鍵把「還沒出貨」的訂單成本
  用最新配方重算（已出貨訂單刻意排除，避免庫存帳對不起來）
- 操作紀錄（所有人的寫入動作都會留痕，只有超級管理員看得到）
- 成員管理（含最後上線時間、核准/移除、角色設定）

## 七、關鍵設計理念

1. **成本鎖定**：訂單成立當下的商品成本會鎖住存進訂單裡，之後商品
   配方再怎麼改，舊訂單的成本數字不會自動跟著變（比照發票開立後
   店家改名不會影響已開發票的精神）。「重算訂單成本」功能可以在
   需要時手動、有範圍地更新（僅限還沒出貨的訂單）。
2. **快照與固定 ID 並存**：訂單裡存的商品名稱是下訂當下的快照
   （保護歷史紀錄準確性），但統計報表用商品/客戶的固定 ID 分組，
   不會因為事後改名字就讓數字被拆散或跑掉。
3. **歷史軌跡不覆寫**：作廢、退貨都是「新增一筆抵銷/標記記錄」，
   不會直接修改或刪除原始資料，保留完整可追溯的軌跡。
4. **危險操作要有防呆**：作廢、永久刪除需要輸入「確認」兩個字；
   出貨有二次確認；批次操作會先列出清單讓人確認過一次。
5. **靜默失敗要避免**：重要的背景動作（登入診斷、Service Worker
   相關）都盡量做成有明確的成功/失敗訊息，不要讓使用者遇到問題卻
   完全看不出發生了什麼事。

## 九、開發時的注意事項（給接手的人看）

- **每次部署都要跑版本號遞增腳本**，JS 跟 CSS 都要處理，不能漏掉
  任何一邊，不然瀏覽器可能會卡在舊快取讓人以為改動沒生效。
- **插入新程式碼時要注意有沒有不小心切斷旁邊既有函式的定義**，
  之前發生過兩次這種事故讓網站掛掉。用 `grep -n "^export"` 比對
  插入前後的函式清單數量是個有效的保護習慣。
- **Firestore 規則有異動的話，需要提醒使用者手動貼到 Firebase
  Console 發布**，光是改本地檔案不會生效。
- **危險/高複雜度的改動先跟使用者討論方向，不要直接動手**，尤其
  是牽涉到資料結構異動、成本計算邏輯、庫存扣款這種一旦做錯很難
  回頭的地方。
