## 2026-08-29　專業視角全面體檢 + 訂單快取優化

針對整個系統做了一次架構/安全/效能審視，發現以下項目：

### 🔴 安全性（最優先）
- ⚠️ **GitHub Token 明文寫在進度文件裡，且設定永不過期**
  → 需使用者自行到 GitHub 後台撤銷並更換為有效期限、範圍限縮的新 token
- ⚠️ **Cloudinary 為無簽章上傳（Unsigned Preset），存在被盜刷流量風險**
  → 需使用者自行到 Cloudinary 後台幫 preset 加上檔案類型/大小/資料夾限制

### 🟡 效能與擴充性
- ✅ **訂單列表頁「一次全撈」問題** → 改成預設只抓近3個月訂單，資料庫端就
  縮小查詢範圍（不是抓全部再篩），並提供「顯示全部歷史訂單」按鈕手動展開；
  同時處理了以下邊界情況，避免「省流量」反而讓資料悄悄消失：
  - 從首頁/通知鈴鐺帶著篩選條件（逾期、待處理、搜尋）進來的一律載入全部歷史
  - 使用者手動把篩選切成「待處理」「已逾期未出貨」「已出貨但未收款」，
    或日期篩選選到3個月以前，都會自動展開抓取全部歷史
  - 匯出 Excel 時，如果選的範圍超出目前已載入的3個月，會先在背景補抓
    完整資料再匯出，避免匯出一份悄悄缺資料的檔案
  - 首頁統計、通知鈴鐺、報表、利潤總覽、客戶詳細頁的訂購紀錄，都沒有動到，
    繼續抓取完整歷史資料，維持原本的準確性
- ✅ **同一批訂單資料被重複抓取**（首頁統計 + 通知鈴鐺各自呼叫一次 listOrders）
  → 已加入 30 秒短期記憶體快取（`js/orders.js` 的 `listOrders()`），
  同一段時間內重複查詢會直接沿用快取結果，不重新打資料庫；
  任何寫入操作（新增/編輯/收款/出貨/作廢/永久刪除，共8個函式）
  都會立即清空快取，確保資料異動後畫面永遠看到最新狀態
- 💬 **首頁統計/通知鈴鐺尚未改用聚合查詢，使用者決定先擱置**（2026-08-29 討論）：
  深入評估後發現這不只是「建一個索引」的小事，而是要先做資料結構異動——
  Firestore 規定「日期範圍」跟「排除某個狀態」不能用在不同欄位的查詢條件裡，
  「已逾期未出貨」這個統計天生需要這兩種條件，所以必須先在每張訂單多存一個
  「目前是否算使用中」的欄位（例如 isActive），查詢才會合法、才能建索引。
  而且舊訂單資料庫裡沒有這個欄位，必須先跑一次性補值程式，否則舊訂單會在
  統計裡「憑空消失」——這對「抓被遺忘的舊逾期單」這個功能來說是最危險的
  副作用。整套是「改資料結構＋補舊資料＋建索引＋改查詢邏輯」，不是單一步驟。
  使用者確認目前用法沒有感覺到變慢，決定先擱置，不現在做。
  → **之後如果要重啟這個項目，直接參考這一段的技術評估即可，不用重新分析。**
- 💬 **商品清單「一次全撈」尚未處理**：商品項目數量通常比訂單少很多，
  暫時優先度較低，之後有需要再討論

### 🟢 工程維護面
- 💬 版本快取號目前靠人工遞增，容易漏改；可考慮寫成一鍵部署腳本或
  GitHub Actions 自動化（尚未實作，優先度較低）
- 💬 沒有自動化測試、沒有預覽環境，屬於小型系統的合理取捨，
  但改動大功能時建議上線前先用不同角色帳號實際測試一輪

### 🔵 商業邏輯／資料面
- ✅ **第二位 superadmin 備援**：原本「可指派角色」選單刻意不含超級管理員
  （保守設計，避免誤開最高權限給不該開的人），使用者明確表示只是要幫
  自己開備援帳號、不開放給別人，已加回這個選項。操作方式：用第二個
  Google 帳號登入一次（會卡在審核中畫面），再用原帳號到「待審核申請」
  核准、角色選「超級管理員」即可，全程在前台操作，不用碰資料庫

## 討論記錄：訂單/商品清單分頁化

**問題：** `listOrders()`、商品清單目前都是 `getDocs()` 一次撈出全部文件，
沒有使用 `limit()` / `startAfter()` 做游標分頁，訂單量成長到幾千筆後
會拖慢載入速度、增加 Firestore 讀取成本。

**已實作（2026-08-29）：訂單列表頁預設近3個月範圍**
沒有採用「一次抓30-50筆、捲到底載入下一批」的傳統游標分頁，因為訂單列表頁
的搜尋/篩選（訂單編號、客戶、電話、日期區間、出貨狀態）目前都是在瀏覽器端
針對已下載的資料做篩選，如果改成游標分頁，篩選功能只能搜到「已經載入的那幾批」，
搜尋準確度會出問題。改用風險較低的做法：查詢時直接在 Firestore 端加上
「日期 ≥ 3個月前」的條件，一次抓進來的資料量自然變少，篩選功能完全不受影響，
需要看更早資料時再讓使用者主動展開。

**尚未實作／可再討論的方向：**
1. **首頁統計數字／通知鈴鐺**：不要抓整份訂單文件回來自己數，
   改用 Firestore 的聚合查詢 `count()`（搭配 `where` 條件）直接在
   資料庫端算出數量，前端不需要下載完整資料。技術卡點：`count()`
   搭配「日期範圍」+「排除某個狀態」這種跨欄位條件時，Firestore
   不允許這樣查詢，必須先在訂單多存一個「是否使用中」的欄位
   （例如 isActive）才能查，而且舊訂單需要先跑一次性補值程式，
   否則舊訂單會在統計裡「憑空消失」。完整評估見上方
   「首頁統計/通知鈴鐺尚未改用聚合查詢」條目。
   **2026-08-29 使用者決定：目前用法沒感覺到變慢，先擱置不做**
2. **商品清單分頁化**：商品項目數量通常遠少於訂單，優先度較低
3. **進階選項（複雜度較高，非必要）**：改成「異動時就同步更新一份統計文件」
   的寫法，讀取時直接讀那份摘要文件，完全不用查詢原始訂單集合。
   效能最好但複雜度高，建議資料量真的成長到有感變慢時再考慮

## 2026-08-29　移除成員後未即時登出的修正

- ✅ **修正「被移除後沒有立刻被踢出畫面」**：原本成員被移除/角色被拿掉時，
  如果他當下正在使用網頁，系統不會主動反應，要等他自己重新整理頁面才會
  發現。現在改成即時監聽自己的成員資料（`js/auth.js` 的
  `watchMembershipLive`），一旦被移除、角色被清空、或狀態變成非
  active，會立刻自動登出並跳出提示告知原因，不用等使用者自己重新整理，
  也不會讓他停留在已經失效的畫面上操作到一半才發現全部失敗
  （附帶好處：角色被即時調整時，暫存資料也會同步更新）
- 💬 **暱稱資料在成員被移除後不會一起清掉**（`publicProfiles` 集合），
  屬於保留特色而非漏洞，若之後想改成「移除時一併清空暱稱」可再討論，
  優先度低，暫不處理

## 2026-08-29　一鍵備份 + PWA（加到主畫面）

- ✅ **一鍵備份**：側邊欄新增「資料備份」（超級管理員限定），一鍵把訂單、
  商品、進貨/領用/盤點記錄、客戶、分類、單位、支出、操作紀錄、成員
  共11個集合完整匯出成一個 JSON 檔案下載。已知限制：暱稱資料
  （publicProfiles）因為 Firestore 規則設計上禁止「列出全部」
  （防止有心人士掃出全部成員信箱），沒辦法一併匯出，其餘商業資料
  都完整包含。建議定期（例如每個月）手動下載一次，存在系統以外的
  地方比較安心
- ✅ **PWA（可加到手機主畫面、像 App 一樣開啟）**：新增 `manifest.json`、
  三種尺寸的品牌圖示（沿用登入畫面的「心」字設計）、極簡版
  `service-worker.js`。特別把 Service Worker 設計成**完全不做任何快取**
  ——因為這個專案本來就有「每次部署手動遞增版本號」的機制防止使用者
  看到舊版本，如果 Service Worker 又自己快取一份，兩套機制會互相打架，
  反而更容易卡在舊版本。目前只負責滿足「可安裝」的技術條件，之後真的
  需要離線瀏覽功能再回頭擴充。手機瀏覽器選單裡的「加入主畫面」
  之後就會出現獨立圖示，開啟後沒有網址列，體感更像一個 App

## 2026-08-30　新增退貨流程

- ✅ **退貨功能上線**：訂單詳細頁（限已出貨、未作廢的訂單）新增「登記退貨」
  按鈕，可以選擇要退哪些商品、退幾件、要不要加回庫存，系統自動算出退款
  金額。設計精神比照作廢訂單——不直接改動原始訂單內容，而是新增一筆
  獨立的退貨記錄（`orderReturns` 集合），保留完整歷史軌跡
  - 訂單累加一個 `returnedAmount` 欄位，收款狀態、應收/應退金額計算
    （`getPaymentStatus`、新增的 `getOutstandingBalance`）都會自動扣除
    已退貨金額；如果客戶已經付清、後來又退貨，畫面會顯示「應退還客戶
    $X」而不是誤判成已結清
  - 加回庫存的機制新增獨立函式 `restockFromReturn`（不是共用領用函式
    傳負數這種容易誤讀的寫法），領用記錄列表會顯示「退貨回補 +N」
  - 已加入防呆：退貨數量不能超過「當初賣出數量 － 之前已經退過的數量」
  - 附帶修正一個潛在 bug：`voidRecord`（作廢庫存記錄）原本沒有特別處理
    「退貨回補」這種方向相反的記錄，如果有人把一筆退貨回補記錄作廢，
    庫存會被錯誤地疊加扣兩次，已修正為依 `source` 判斷正確的調整方向
  - 利潤總覽、統計報表原本算營收/客戶消費/收款狀況都是直接用訂單總額，
    沒有扣退貨金額，會虛報數字，已一併修正（訂單層級的營收數字都已經
    正確扣除；商品/分類層級的銷售排行**尚未**扣除，屬於已知限制，
    見下方待辦）
- ⚠️ **需要手動到 Firebase 後台操作**：`firestore.rules` 已經加入
  `orderReturns` 集合的規則（讀取：全部有效成員；新增：管理員以上/
  訂單進出貨人員；不可修改刪除，比照操作紀錄的精神保留稽核完整性），
  **但這份規則只是存在 repo 裡，還沒有真的生效**。需要使用者自己把
  `firestore.rules` 整份內容複製貼到
  [Firebase Console 的 Firestore 規則頁面](https://console.firebase.google.com/project/heartfelt-order/firestore/rules)
  覆蓋貼上，然後按「發布」，退貨功能才能真的運作（不然新增退貨記錄
  時會被規則擋下來，跳出權限錯誤）
- 💬 **已知限制**：退貨如果有加回庫存，理論上當初認列的銷貨成本
  （COGS）也應該跟著沖銷一部分，不然毛利會被低估一點點；另外商品/
  分類銷售排行（`reports-ui.js` 的 topProducts/categoryStats）目前
  還沒扣除退貨數量。這兩個都需要更細緻的資料比對（要把退貨記錄跟
  原始訂單品項一一對應），優先度中等，先記錄下來，之後有空再處理

## 2026-08-30　客戶資料的訂購管道改成下拉選單

- ✅ **修正客戶資料頁面「訂購管道」是自由輸入文字框的問題**：訂單建立
  頁面的訂購管道本來就是下拉選單（LINE/IG/FB/現場/其他，選「其他」才
  能自訂文字），但客戶資料頁面卻是純自由輸入，同一個管道容易被打成
  不同寫法（例如「LINE」跟「line」），統計時會兜不起來。已改成跟訂單
  頁一致的下拉選單
  - 把 `ORDER_CHANNELS` 清單抽到 `contacts.js`（資料層）當單一資料
    來源，訂單頁跟客戶資料頁共用同一份，不會各自維護出兩份不一致的清單
  - 把 `openCustomTextModal`（選「其他」時跳出的自訂文字輸入視窗）
